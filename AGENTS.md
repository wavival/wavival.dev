# AGENTS.md

Guidance for AI coding agents working in this repo. See `CLAUDE.md` for full project context, stack, and conventions.

## Rules

- **Lúmina W delivery flow.** `main` is production, `stg` is staging, and `dev` is the integration base. Create human work branches from `dev` with `feature/*`, `fix/*`, or `chore/*` names, then open every work PR to `dev`. Promotions move only `dev` to `stg` and `stg` to `main`; Valentina merges both promotion PRs manually. Do not push directly to `dev`, `stg`, or `main`. Do not merge or promote while any required check is pending, failing, cancelled, skipped because of another failure, or unavailable. After a work branch is merged into `dev` and the merge is confirmed, delete the local and remote branch. Dependabot opens automated dependency PRs to `dev`.

- **Commit messages.** Use strict Conventional Commits in English: `type(scope): message`. Allowed scopes in this portfolio repo are `api`, `ui`, `db`, `auth`, `ci`, `deploy`, `docs`, `config`, `tests`, `security`, `deps`, `core`, `seo`, and `a11y`. The local `.husky/commit-msg` hook and the CI `commitlint` job both enforce this.

- **Delivery checks.** Required delivery checks for protected branches are `commitlint`, `quality`, `tests`, `security scan`, and `validate-pr-base`. The `quality` job runs dependency audit, format check, lint, Astro type check, build, and CSP hash verification. The `tests` job runs Playwright. The `security scan` job runs gitleaks with the org-level `GITLEAKS_LICENSE` secret. The `validate-pr-base` workflow blocks skipped promotion paths.

- **No em dashes.** Never use the em-dash character (Unicode U+2014) anywhere in this repo: copy, code, comments, docs, commit messages, or PR descriptions. Use normal punctuation instead:
  - colon (`:`) when the second part explains the first,
  - comma (`,`) for a light aside,
  - parentheses (`( )`) for a parenthetical (especially when the aside already contains commas),
  - hyphen (`-`) for ranges or simple separators.
  - This applies to both generated and edited content. Do not substitute an en-dash (`–`) or any other fancy dash either; plain ASCII punctuation only.

- **No arrows or icons in buttons/links unless asked.** Never add `←`, `→`, `↑`, `↓`, or any decorative icon to a `Button` or `Link` component unless Valentina explicitly requests it. The components communicate action through their design; adding unsolicited arrows is a style override she will revert.

- **Keep docs in sync (ALWAYS, mandatory).** ALWAYS update both `CLAUDE.md` and `AGENTS.md` in the same change whenever ANY important change happens in the repository. Non-negotiable, no exceptions. "Important" includes (but is not limited to): infrastructure, dependencies, tooling, repo structure/file layout, build or deploy config (`netlify.toml`, CI), routing/i18n conventions, SEO / schema / JSON-LD / metadata, analytics, design-system or token decisions, and accessibility behavior. Treat the docs as part of the change, never a follow-up: if a change makes any statement in either file wrong or incomplete, fix it before finishing. Applies to Claude and all subagents, every time.

- **Bilingual routing.** ES is the default at root with Spanish slugs (`/proyectos`, `/servicios`, `/sobre-mi`, `/contacto`, `/herramientas`, `/privacidad`); EN mirrors under `/en/` with English slugs. Never hardcode a route that ignores language: use the `isEn ? "/en/..." : "/<es-slug>"` ternary in components, and update the slug map in `src/i18n/utils.ts` (`EN_PAGE_MAP` + `getAltLangUrl`) whenever you add a page or rename a slug. `EN_PAGE_MAP` is exported and also consumed by the sitemap `serialize` hook in `astro.config.mjs`, which emits reciprocal `xhtml:link` hreflang alternates (`es` / `en` / `x-default`, trailing-slashed) for every bilingual URL. Use the bare language codes `es`/`en` (one Spanish/English version each, targeting all speakers), never region codes (`es-CO`/`en-US`), to match the page-head `alternates` and avoid wrongly narrowing geo-targeting. Legacy English-word ES routes 301-redirect to the Spanish slugs in `netlify.toml`. `getAltLangUrl` special-cases `/404` and `/en/404`: both redirect to the opposite locale's home rather than a translated error page. Translatable data lives in bilingual fields, not just UI strings: `src/data/stack.ts` carries `descriptionEn` / `whyEn` / `toolsEn` (the latter only on categories with translatable chips, e.g. Design & UX, Product Engineering; falls back to `tools` for proper-noun-only categories), rendered via `isEn ? (s.toolsEn ?? s.tools) : s.tools` in `Stack.astro` and `s.toolsEn ?? s.tools` in `/en/uses`. When you add a Spanish chip/label to a data file, add its `*En` counterpart too. The OKroot case study (visible brand `OKroot`, formerly `Root`) intentionally keeps the slugs `root` and `root-landing` for URL stability: do not rename the slug to match the brand. Only the Linux-privilege `Root:` strings in the Forgotten Portal CTF data are unrelated and stay as-is.

- **SEO and JSON-LD conventions.** All hreflang `href` values and BreadcrumbList/Service `item`/`url` values must carry trailing slashes to match canonical URLs. `Person.image` is an `ImageObject` node (not a bare URL string). `Organization.logo` is an `ImageObject` node. `Person.description` in the `@graph` is a stable Spanish bio constant, not the page-level meta description. The `WebSite` node omits `inLanguage` (shared `@id` must not mutate per locale). `og:image:type` is derived from the OG image file extension (`.webp` yields `image/webp`). `og:type` is per page via the `ogType` Layout prop: `website` (default), `profile` (home), `article` (case studies, which also emit `article:published_time`/`article:modified_time` from `ogPublishedTime`/`ogModifiedTime`). Case studies use per-project OG cards (`project.image`, 1200x630 webp in `public/images/`: `og-terracore`/`og-okroot`/`og-nullbreach`) and per-project `og:image:alt` / `twitter:image:alt` via the `ogImageAlt` Layout prop (from `project.imageAlt`, EN from `project.en.imageAlt`), falling back to the generic locale alt; regenerate OG cards as 1200x630 webp with `sharp`. Service nodes carry `@id` and `priceRange`. Both `ContactPage` pages (`/contacto` and `/en/contact`) also emit a `BreadcrumbList`. Case-study nodes carry an `@id` (`<pageURL>#project`); `SoftwareApplication` nodes use real `programmingLanguage` values (Python, TypeScript, SQL), move frameworks/tools to `softwareRequirements` (from `project.stack`), and set an accurate `applicationCategory` (`project.appCategory`). Case-study `datePublished`/`dateModified` (JSON-LD and the visible date) come from `project.datePublished`/`dateModified` in `src/data/projects.ts` and fall back to the build date only if unset: every project now sets real dates, so `dateModified` no longer churns on each deploy. Set real dates there, never hardcode. In the JSON-LD these are emitted as full ISO 8601 datetimes (`toIsoDateTime()` normalizes a date-only `YYYY-MM-DD` to `YYYY-MM-DDT00:00:00-05:00`; Google's Profile page rich result rejects date-only `dateModified`); the visible label stays date-only. `Organization` carries a `contactPoint`; its `sameAs` excludes its own `url`. `Person.sameAs` uses canonical www + trailing-slash profile URLs. The sitemap `serialize` hook sets a per-type `priority` (home 1.0, sections 0.8, case studies 0.7, legal 0.3). The hero image preload (`<link rel="preload" as="image">` for `profile.webp`) is gated behind the `preloadHero` Layout prop and set only on pages that render the photo (home, about). Twitter cards set `twitter:site`/`twitter:creator` (`@wavival0`), and `Person.sameAs` includes the X profile (`https://x.com/wavival0`). Keep titles <=60 and meta descriptions <=160 characters. `public/llms.txt` (index) and `public/llms-full.txt` (long-form companion, linked from the `## Optional` section) must stay in sync with site content (project metrics, stacks, services, contact).

- **Testing.** Run `npm run build` then `npm test`. Playwright serves `dist/` via its own `astro preview` on port **4329** with `reuseExistingServer: false`, so a dev server on 4321 is never reused (a dev server has no sitemap and uses localhost canonicals, breaking the SEO/i18n specs). Every standalone page needs exactly one `<h1>`: section components reused as full pages (e.g. `Projects`) take a `heading="h1"` prop, since their default top heading is `h2` for the homepage where `Hero` owns the `h1`. The route-coverage spec asserts this. Some specs are pure unit tests (no browser): `redirects.spec.ts` parses `netlify.toml` to lock the legacy 301s, `i18n-utils.spec.ts` tests `getAltLangUrl` directly. Update these when you change redirects or the slug map.

- **CI gates (`.github/workflows/ci.yml`).** `commitlint` enforces pull request commit messages. `quality` runs dependency audit via `npm audit --audit-level=high --omit=dev`, format check, lint via `npm run lint`, type check via `astro check`, build, and CSP hash verification. `tests` runs Playwright, `lighthouse` asserts perf/a11y/best-practices/SEO via `lighthouserc.json`, `links` checks built internal links, and `security scan` runs gitleaks. Run `npm run build` before `lhci`/`links` locally. CI jobs pin Node via `node-version-file: ".nvmrc"` (→ `22`). ESLint uses a flat config (`eslint.config.mjs`: `eslint-plugin-astro` + `typescript-eslint` + `eslint-config-prettier`); Husky runs `lint-staged` on pre-commit and commitlint on commit-msg, so keep the lint and commit-message baselines clean. Favicon/manifest icons in `public/` are generated from `brand/logo-w.webp` with `sharp`; regenerate them if the logo changes. Dependabot opens weekly dependency PRs to `dev`, but ignores `tailwindcss` major bumps so Tailwind stays on v3 until a planned migration. Security contact lives at `public/.well-known/security.txt` (RFC 9116); bump its `Expires` date before it lapses. `CHANGELOG.md` follows Keep a Changelog + SemVer: add entries under `[Unreleased]` as you ship, and cut a version section on release.

- **One accessible interactive blue.** All interactive blues resolve to a single value per theme: `#1565c0` (light) / `#5b8cff` (dark). `--accent-link` (link + icon-anchor text, `.btn-ghost` border/text), `--btn-bg` (`.btn-primary` fill, `.btn-ghost` hover fill), and `--brand-blue-text` (small `text-xs`/`text-sm` blue: subtitles, chips, labels, filter buttons) all use it, so buttons and icon anchors render the same blue. White-on-`#1565c0` button text is 5.67:1; the same blue as link text is 5.13:1 (light) / 5.93:1 (dark), all >=4.5:1. `--brand-blue` (#407bff) fails AA for small text (~3.4:1) and is reserved for fills, borders, and large/display text only. Do not reintroduce a brighter blue for button fills (the retired dodger-blue accent failed white text at 3.24:1). Project `blue` tag chips use `text-blue-900`/`dark:text-blue-300`. Every interactive element carries `focus-visible:ring-2 focus-visible:ring-[var(--accent-link)]` (utility classes `.btn-primary`/`.btn-ghost`/`.link` plus NavBar toggles/hamburger). The blue UI SVGs in `public/icons/ui/` hardcode `fill="#1565c0"` (loaded via `<img>`, so CSS/tokens cannot recolor them: edit the files to change). Calendly's `primary_color` is also `1565c0`. Caveat: in dark mode those `<img>` icons stay `#1565c0` (passes the 3:1 graphic rule on the dark bg) while blue _text_ switches to `#5b8cff` via the token, since a single static SVG cannot be re-themed.

- **Accessibility behaviors to preserve.** Mobile menu is `inert` while closed and traps focus while open (`src/scripts/nav.ts`); Escape restores focus to the hamburger. NavBar/Footer mark the active page with `aria-current="page"` via `isCurrent()`. Footer group titles are real `<h2>`s. The theme toggle sets a state-aware `aria-label` in `theme.ts`; the hamburger's `aria-label` is localized and state-aware too (NavBar passes `data-label-open`/`data-label-close` from the `nav.openMenu`/`nav.closeMenu` translations, `nav.ts` reads them on toggle, never hardcoding Spanish). Icon-only links keep a >=44px hit target. The `Loader` is hidden via `<noscript>`. Any control with visible text must keep that text inside its `aria-label` (Label-in-Name). The project filter "no results" block is `role="status"` (WCAG 4.1.3) so an empty filter result is announced. The single `<meta name="theme-color">` is driven by JS (`theme.ts` `syncIcons` + the pre-paint inline script), not media queries, because the class-based theme can diverge from the OS `prefers-color-scheme`.

- **Analytics and RUM.** Umami (cookieless) and Core Web Vitals RUM (`src/scripts/vitals.ts`, the `web-vitals` package) are both gated on `PUBLIC_UMAMI_SRC` + `PUBLIC_UMAMI_ID`: neither the analytics script nor the vitals bundle is emitted unless both are set. Vitals report LCP/INP/CLS/FCP/TTFB to Umami as `web-vitals` custom events over `connect-src` (both `cloud.umami.is` and `analytics.umami.is` are in the CSP `script-src` + `connect-src`). Do not add a third-party RUM/error service without updating the CSP. The CSP `script-src` is **hash-based (no `'unsafe-inline'`)**: it carries a `sha256-*` for every inline `<script>` Astro emits, recomputed from `dist/` by `scripts/check-csp-hashes.mjs` (`npm run csp:check`, in the CI `quality` job). Adding or editing ANY inline script (theme, reveal, `define:vars`, etc.) changes its hash and is blocked in production until the new hash lands in `netlify.toml`; run `npm run build && npm run csp:check` to print it. JSON-LD (`application/ld+json`) is a data block and not gated; `style-src` keeps `'unsafe-inline'` (inline `style` attributes hashes can't cover). CTA click tracking uses Umami's zero-JS automatic capture: key CTAs carry a `data-umami-event="<name>"` attribute (no `window.umami.track()` calls). `Button.astro` and `Link.astro` forward a `data-umami-event` prop; project app/site links carry an optional `event` field on `ProjectLink` (`src/data/projects.ts`) forwarded by `Projects.astro` and both `[slug].astro` pages. Event names: `cta-quiero-producto`, `cv-descarga-es`/`cv-descarga-en`, `contacto-email`/`contacto-whatsapp`/`contacto-calendly`, `ver-app-terracore`/`ver-app-root`/`ver-app-nullbreach`. Add new CTA tracking via this attribute, never inline scripts.

- **GitHub widget (build-time).** `/herramientas` and `/en/uses` render a GitHub profile + non-fork repos via `fetchGithubProfile` in `src/data/github.ts`, called from Astro frontmatter (build-time, no client JS, no token), inside the `#repos` section. It is unauthenticated (GitHub's ~60 req/h per IP) and fails soft: any network error or rate-limit returns nulls, so the build never breaks and the widget is simply absent that build (`{githubUser && (...)}` guards the markup). No CSP change is needed since the fetch is server-side at build, not in the browser. `curateRepos()` partitions the repos into a flagship spotlight and a learning-resources grid: `FEATURED_REPOS` (`nullbreach-api` + `nullbreach-web`, in that order, under a "Destacado"/"Featured" NullBreach card: no left accent, gradient `bg-blur`→`bg-card` container with a solid `--btn-bg` badge pill + white text for AA) and `HIDDEN_REPOS` (`wavival` profile README, `wavival.dev` portfolio, `prueba-tecnica-logika` one-off test); everything else is "Recursos para aprender"/"Resources to learn from". Re-pin or hide a repo by editing those arrays, not the markup. Both tiers render through `RepoCard.astro` (props: `repo`, `lang`, `variant`: `featured` uses `.card`, `resource` uses a thin-border card that lifts + highlights its border to `--brand-blue` on hover with a monospace name), keeping ES/EN and featured/resources DRY. Cards use design tokens (no `<style>` blocks, no nonexistent `--color-*` tokens); the repo name is a plain `<span>` (not `<strong>`), language shows a small `--brand-blue` dot, and star counts render as localized text (`estrella(s)` / `star(s)`), not a `★` glyph, per the no-decorative-icon rule. The card `<a>` carries no `aria-label`, so its accessible name is the visible content (name + description + language + stars), keeping screen-reader and visual info parity.

- **Netlify secrets scanning.** `SECRETS_SCAN_OMIT_KEYS` in `netlify.toml` `[build.environment]` excludes the `PUBLIC_*` keys (`PUBLIC_UMAMI_SRC`, `PUBLIC_UMAMI_ID`). They are client-exposed by design, so their values legitimately appear in repo docs and the built bundle; without the omit, the scanner fails the build. Add any new `PUBLIC_*` key to this list.

- Follow all conventions in `CLAUDE.md` (design tokens, dark-mode via `.dark` class, static-only Astro, accessibility, etc.).
